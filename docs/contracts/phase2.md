## Layout
- **Integers only:** `canonicalJson` only takes integers, so lengths are world units ×1000 (`…Milli`) and angles are thousandths of a turn.
- **Ids:** every body is keyed by the snapshot's stable `DirId` / `FileId`. Paths are for labels only.
- **Content roots (amended 2026-11-11, #71):** in most repos one folder (`src/`, `lib/`, `packages/`) holds most of the code, so as one planet it hid the structure that matters. The human decided (2026-11-11, `docs/features/content-roots.md`) that the user can name one or more content roots. `source.roots` lists them: repo-relative, sorted, no trailing slash. `[]` is #18's mapping, where every top-level folder is a planet. A root's direct subfolders holding a surface file are **content** planets (`Planet.zone: 'content'`), on the inner orbits. Every other top-level folder holding one is an **outer** planet, on orbits beyond them: content planets take slots 0 to `CONTENT_SLOTS - 1` and outer planets start `OUTER_GAP_SLOTS` empty slots later (layout constants), so neither zone's growth moves the other's planets. A content planet born while every content slot is taken goes to the innermost free slot past the gap. Partners are older planets in the same zone. A root is never a planet itself. A file directly inside a root is a star moonlet of kind `root-file`. With `roots: []` every planet is `outer`, and the layout is #18's apart from the two new keys. Fog's `planets` covers both zones, by the same rule (`planetHome` in `src/core/structure.ts`). The view accepts the fields and needn't style zones yet.
- **Orbits:** slot 0 is innermost. `slotSpacingMilli ≥ 2 × maxPlanetRadiusMilli`, so growth never forces a move (#18). `phaseMilliturn` is the frame-0 angle. Orbital motion is the renderer's job, as a function of frame number.
- **Surface:** a Fibonacci sphere of `grid.cells` cells. Cell `i` is centred at `fibonacciCell(i, cells)`, and both `layout()` and the renderer use that one helper. "Nearest free cell" means nearest by angle.
- **Overflow is counted, never dropped (Rule 1):** `moonOverflow`, `surface.overflow`, `moonletOverflow`.
- **Health:** `band` is one of `lava | toxic | ash | healthy`. A healthy planet is drawn as lush, ocean or ice, picked by `biomeSeed`. Thresholds live in one constants file owned by #18. `qodoUnknown` is true exactly when `qodoOpen` is null. Unreadable debt is counted in `debtUnknownFiles`, never as 0.
- **Seeded variety:** `biomeSeed` only varies the look inside a band (principle 4).
- **No rings (amended 2026-11-10):** the human decided on 2026-11-09 that rings no longer mean unmerged branches. Their meaning is open, so the layout has no rings and the product view draws none. Stale branches belong to debris (R13), later. See art-direction §6 on `docs/art-meaning`.
- **#23 (decided by the human, 2026-11-09):**
  - Partner detection looks through merge commits to the merged branch's own commits.
  - Test data (non-test files under a test folder) rides with the tests. It is never a planet or surface, and is counted in `star.testData`. So `test/` is never a planet.

## Fog view
- **Levels (amended 2026-11-24, #201, understanding mode U1–U3; schema `fog.2`):** each file's `state` is one `FogLevel`:
  - `fogged`: a content change you didn't write (agent, mixed, teammate, unknown) is newer than the file's last review, or its history can't be followed (`lineage-unknown`, Rule 1);
  - `haze`: seen, not yet understood. Every such change is reviewed (a chart, a passed quiz or the baseline), or there was none (yours only, or no change in the window). **Shown as "misted"** (#224; the human, 2026-11-25: "misted for read but untested"): the view, the directory view and `commet chart status` say "misted" (or "misted (read)"); the stored value, the API and every contract field stay `haze`, with no migration;
  - `clear`: understood. A quiz on this version was passed (`QuizPass`) and no content change, anyone's (yours too), came after it.
  - **Changes re-haze (U2):** a cleared file whose content changes drops to `haze` on the next scan and stays there through further changes, never straight to `fogged`, until a new quiz clears it. A pure rename or mode change isn't a content change. History that can't be followed past the quiz (a window gap, an unsure birth, a name two files claim) fogs it with `lineage-unknown`, as for any file; once a later chart or baseline covers that history, the file is `haze`, never `clear`, until a new quiz. A quiz outside the window clears nothing.
  - fog.1's `charted` and `clear` both mean `haze` now: fog.1's `clear` meant "nothing to review", not "understood". The view refuses any other `schemaVersion`, fog.1 included, so an old or damaged answer draws every file fogged (Rule 1).
- **Reasons:** `agent`, `mixed`, `self-committed-agent-written`, `teammate`, `unknown`, `lineage-unknown`. Unknown is never yours. Only a fogged file has any.
- **Coverage:** `files` lists every file in `snapshot.files`, including surface overflow, sorted by `fileId`. Planet and star counts (`FogCounts`: `total`, `fogged`, `haze`, `clear`, with `fogged + haze + clear === total`) add up to `files.length`. Star counts include root files, unmatched tests and test data.
- **Mastery (U3):** a planet's `clear / total`, by count, shown on its info panel as a whole percent rounded down (`masteryPercent`, `src/core/mastery.ts`), so it never says 100% while a file isn't clear; `commet chart status` prints it per planet. The fog draws the same counts: clear files have nothing over them, misted (`haze`) ones thin mist.
- **`charted`:** true when a chart or a passed quiz of a file is placed in the window (the baseline aside). The view offers the first-run baseline only while it's false (fog.1 told it by the `charted` state).
- **No wall-clock time anywhere:** `baseline` and `since` are commit SHAs.
- **Chart state on disk** (`.git/commet/chart.json`) is private to #33. Others only see `FogView` and send `ChartAction`. Since #201 it is `chart.2`: `{ schemaVersion, charts, clears, baselines }`, file ids and commit SHAs only. `charts` are haze (seen) and `clears` the quizzes passed, each `{ fileId, at }`, sorted and unique, a newer entry of a file dropping its older ones. **Migration:** a `chart.1` file (no `clears`) reads as `chart.2` with none, so everything it charted is haze, never clear; the next write saves it as `chart.2`. Anything else is a state error, never reset (golden: `test/golden/chart-migration.json`).
- **Quiz passes (`QuizPass`, `{ fileId, at }`)** aren't a `ChartAction`: no route, button or CLI command takes one (AGENTS.md Rule 6: fog clears only when a question is answered). The quiz (#203) records a pass with `writeQuizPass` (`src/state/chart.ts`) once it has checked the answers; it is recorded at `at` like a chart (#58), so a change newer than the version quizzed leaves the file haze.
- **Opening a file in the review panel (AC2):** opening a fogged file's diff, when the panel shows the whole change as text (not cut, no binary part, every part with a text hunk), posts the same `chart` action at the diff's `at`, so the file moves to haze, never to clear. A cut or binary diff, or one with a part git shows no text for (only a mode change, a bare rename), waits for Chart, as before.
- **Drawn (#224, #228, art-direction §9 "fog of war is cloud"):** fogged is the planets' own cream weather over the file's territory, locked to the ground, in the weather's noise pattern at 0.35 of the planet's sites (its clear sky shows the ground and its health), each file keeping at least half that over its own highest sites; misted (`haze`) is a little thin weather (0.1 of the sites) in the cloud's light steps, white wherever lit, with no shadow; clear has nothing over it. Nothing darkens the ground: no veil at any level, nor for unknown fog, which draws every file fogged (Rule 1). Moons: all cloud, a thin mist line round the equator, or nothing. Fronts run between any two levels: a chart turns the file's cloud [OIII] teal while it thins to mist, a passed quiz fades the mist, and a change or new fog rolls cloud (or mist) in from the territory's far edge with no teal. Under reduced motion every change snaps.
- **Every `ChartAction` carries `at`** (#58, amended 2026-11-11): the `FogView.head` the user was looking at, as a full SHA. The write is recorded at `at`: a chart or baseline covers changes up to `at` and no further. So if a scan lands after the view's last fetch, a change that arrived unseen (say, a new agent commit) is newer than `at` and stays fogged, with no false clear (AGENTS.md Rule 1), no refusal and no race. `at` must be a commit the current snapshot knows (in its window, on HEAD's first-parent line). Otherwise (another branch, before the window, a snapshot that went backwards) the write is refused with `{ ok: false, error: 'unknown-head', head: <current> }` (`ChartUnknownHead`) and nothing is written; the view refetches and asks again. For `chart`, `fileId` is the file's id as of `at` and must lead to a file at HEAD. `baseline-undo` pops the last baseline. `commet chart` uses the current head.

## Drone view (amended 2026-11-13, #80)
- **What it is:** one `DroneSession` per agent session in the snapshot, sorted by `key`, plus `total`, `placed` and `needsRescan`. It is served at `GET /api/drones` and holds nothing the snapshot's sessions don't already hold.
- **Safe fields only (Rules 2 and 6):** key, seed, tool, kind, parent, agent type, start and end, branch, model, `inferred` and `home`. No paths, commit subjects, prompts, or per-session line, file or commit counts in the drone list. Per Rule 6's 2026-11-16 amendment, an agent session's own detail view may later show its edited files, edit counts and edit times (a separate, per-session request); never for pseudo-sessions (`inferred`), never ranked, compared or summed per person. Branch, model and agent type already pass the parser's `metaToken` filter.
- **`home`:** the planet's `DirId`, `'star'`, or null. It is built from the session's `files` and the fog's `FogBase.home` map (`openFogSource`), so drones and fog agree on where a file lives, and #64's pair check covers drones too. The planet holding most of the session's files wins, with ties broken by codepoint. A session with no files of its own is null, except that a subagent takes its parent's home. Null is counted and never drawn or guessed (Rule 1).
- **`needsRescan`:** true when the snapshot has no `Session.files` (it was scanned before #80). Every `home` is then null. This is the lead's reading of the human's decision on #80's default 4: an old snapshot is not refused, and the view says "rescan to place drones".
- **Tool:** `tool` is a string, not the snapshot's `Tool` union, so a provider the scanner doesn't know yet draws the generic drone with its name.
- **Determinism:** the view is a pure function of the snapshot and the layout. Two scans of the same repo and logs give byte-identical `canonicalJson`. No wall-clock time (principle 3).

## Drone detail (amended 2026-11-18, #148)
- **What it is:** one agent session's own detail for the drone panel: its files at HEAD with an edit count each, a count of its other edited paths and their edits, and its edits in `DETAIL_BUCKETS` (24, fixed) equal time slices. `GET /api/drone-detail?key=<SessionKey>&at=<Sha>` (`DroneDetailQuery`, `DroneDetail`) serves it, one session per request, for the drone the user selected. The list route `GET /api/drones` is unchanged and stays path- and count-free.
- **Rule 6:** this is the session-detail exception (AGENTS.md Rule 6, 2026-11-16). The answer describes the requested session only: no other session, no ranking and no total across sessions. Files are ordered by folder, then name (codepoint), never by count. A pseudo-session (`inferred`) gets no detail: 404, as an unknown key does.
- **Query:** exactly `key` and `at`, each once. `at` is the `DroneView.head` the view shows and must be the current head, else `ChartUnknownHead` (409) and the view refetches. A malformed query is 400; an unknown key or an inferred session is 404 with a fixed error naming neither. GET only, behind the same Host, origin and token gates.
- **Source:** the snapshot's `Session.fileEdits`, `editsOutside` and `editBuckets` (scanner, #148), read through `openFogSource`, so #64's pair check refuses a snapshot and layout from different scans here too. Paths come from `snapshot.files` and are repo-relative; a path with no file at HEAD is counted in `otherFiles`, never named (Rule 1: it may be deleted, renamed, excluded, on another branch or in a removed worktree, #110).
- **Edits and buckets:** an edit is one tool result's change to one file (the parser's deduped edit events). Bucket `i = span === 0 ? 0 : floor((ts − first) × 24 / (span + 1))`, in integers, where `first` and `last` are the millisecond times behind `startedAt` and `endedAt` and `span = last − first`. The buckets count every edit, so they sum to the files' edits plus `otherEdits`. `spanMs` (amended 2026-11-19) is that `span` in milliseconds, so the panel's words place each slice as precisely as the scanner did; it matches `startedAt`..`endedAt` to within the second they drop.
- **One rule set (amended 2026-11-19):** `src/core/drone-detail-check.ts` holds the rules a snapshot record must meet to be served (`sessionDetailProblems`: the scanner's own identities) and a served detail must meet to be shown (`droneDetailProblems`). The server checks both and the view checks the second, so the server never serves a detail the view refuses; a record that fails is damaged state (500 with the "run `commet scan`" message). It imports only the contract's constants, so the view and the render stand-ins load it.
- **`needsRescan`:** true when the snapshot predates #148 (none of `fileEdits`, `editsOutside`, `editBuckets` and `editSpanMs`). `files` and `buckets` are then empty and the counts and `spanMs` 0, and the view says "rescan to see this session's files".
- **Determinism:** a pure function of the snapshot. Two scans of the same repo and logs give byte-identical `canonicalJson`.

## Beacons (amended 2026-11-18, #79, R10)
- **What it is:** charting a file can leave a one-line note, the captain's log, shown as a beacon on the file's planet (or on the star for a root file or unmatched test).
- **State:** `.git/commet/beacons.json`, never git notes (they attach to commits and can be pushed): `{ schemaVersion: 'beacons.1', beacons: [{ fileId, at, text }] }`, file ids, commit SHAs and the note text only, in the order the notes were left. Canonical JSON, mode 0600, atomic writes under `beacons.lock`, symlinks refused; a damaged file is a state error (exit 5), never reset. No wall-clock time.
- **Recorded like a chart:** `fileId` is the file's id as of `at`, the `FogView.head` the user saw (#58), and it is followed to the current head through the fog's rename map on every read. A renamed file keeps its note; a note whose file can't be followed to HEAD (deleted, another branch, before the window) is counted in `BeaconView.unplaced`, never drawn or dropped (Rule 1). One note per file: a new one replaces the old and moves to the end. Past `MAX_BEACONS` (1000) a new note is refused.
- **The note:** 1 to `BEACON_TEXT_MAX` (120) Unicode code points on one line, no leading or trailing whitespace, and no control (`\p{Cc}`), line or paragraph separator, bidi-control or lone-surrogate character. One rule (`beaconTextProblem`, `src/core/beacons.ts`) is used by the server, the state file, the CLI and the view; a bad note is refused with fixed text that never quotes it, never rewritten. Clients trim surrounding whitespace before sending. It is plain text: JSON data on the wire, DOM `textContent` or bitmap glyphs in the view, never HTML.
- **`BeaconView`** (`GET /api/beacons`): `head`, the placed `beacons` (`fileId` at HEAD, repo-relative `path` for the label, `home` a planet's `DirId` or `'star'` from the fog's `FogBase.home` map, `at`, `text`) and `unplaced`. Like the fog and drones, the view draws it only over the layout of the same scan (#64).
- **CLI:** `commet beacon [list]`, `commet beacon [--] <file> <note>`, `commet beacon --remove [--] <file>`, `commet beacon --remove-unplaced` (removes the notes counted as unplaced, which `--remove` can't name, so the cap never blocks new notes for good), and `commet chart --note <text> [--] <file>`. They act at the head of the snapshot they read; a write whose snapshot changed before it got the lock reloads it first, as a chart write does.
- **The rule's own module:** `beaconTextProblem` lives in `src/core/beacon-text.ts`, which imports only the contract's constants, because the view and the render stand-ins load it; the rest of `src/core/beacons.ts` needs the fog core.

## Co-change (amended 2026-11-23, #211, R9)
- **What it is:** files that usually change in the same commit, from git history in the scan's window only (no AI, no parsers), and the "usually changes with X" flag for a file a strong partner's latest change left out. `commet scan` records them in the snapshot; `GET /api/cochange` serves them to the view.
- **Counting (snapshot `cochange`):** each window commit's content changes by file at HEAD, renames followed through the same path history the fog uses (a pure rename or mode change is no change). For a pair, `both` commits held both and `seen(a) + seen(b) − both` held either; `strengthMilli = floor(both × 1000 / either)` (Jaccard). A pair is kept at `strengthMilli ≥ 150` and `both ≥ 2` (one shared commit is no evidence that they usually change together), and when it is among the 5 strongest pairs of at least one of its files (ranked by strength, then `both`, then the ids), so every file keeps its own 5 strongest and a busy file can appear in more lists. A commit over 200 such files is left out of the counting and counted in `bulkCommits` (system design §5.1.7); it still counts as each file's latest change. The settings (`thresholdMilli` 150, `minBoth` 2, `cap` 5, `flagMilli` 500, `flagMinBoth` 3, `flagWindow` 10, `bulkFiles` 200) are recorded in `cochange.settings` (Rule 1: documented thresholds); the contract's `COCHANGE` holds the same values. Pairs hold file ids, counts and strengths only, `a` < `b`, sorted; no paths.
- **Missing pairs (recent changes only, the human, 2026-11-23):** for a kept pair at `strengthMilli ≥ 500` (the strong step) over at least 3 shared commits (`flagMinBoth`; pairs themselves need 2), a file is flagged "usually changes with <partner>" when the partner changed in the last 10 commits at HEAD (`flagWindow`: first-parent seqs above HEAD's minus 10) and the file didn't, with `at` the partner's latest change. An older skip counts as settled and isn't flagged. One flag per file, for its strongest such partner (then the partner first by id). A later change that touches the flagged file, a bulk one included, clears it at the next scan, and so does `at` leaving the window.
- **The view (`CoChangeView`, `GET /api/cochange`):** `links` (the pairs, `strengthMilli` only), the `flags` still standing, `dismissed`, and `files` (each file a link or flag names: its repo-relative `path` for labels and its `home`, a planet's `DirId` or `'star'`, from the fog's `FogBase.home` map). A flag is dismissed, and counted, once its file is reviewed through `at` or later by a chart of it or a baseline, as the fog counts a review (#211: charting the partner dismisses it). Built from the same snapshot/layout pair as the fog (#64's check); a damaged record is a state error (500, "run `commet scan`"). `needsRescan` is true for a snapshot from before #211, with nothing else. The view refetches it on layout loads and snapshot and fog events (a chart changes the flags).
- **Steps:** weak from 150, mid from 300, strong from 500 (`COCHANGE_STEPS`); the view draws one, two or three beads by step (art-direction §10).
- **Render hook:** `RenderInput.cochange` (of the layout's head, checked by the view's validator) and `RenderInput.focus` (`{ dirId, fileId? }`, focused from frame 0, so the lines draw in from frame 0, or at once under reduced motion).
- **Determinism:** a pure function of the snapshot (and, for the view, the chart state). Two scans of the same repo give byte-identical `canonicalJson`.

## Crew (amended 2026-11-25, #207, U8)
- **What it is:** one astronaut per human author in the scan window, from local git history only (no network, R6), and one crew member's own panel. `GET /api/crew` serves the crew (`CrewView`) and `GET /api/crew-detail?person=<PersonId>&at=<Sha>` one member's panel (`CrewDetail`). Teammates get no drones: drones are your own agent sessions only (C6).
- **People in the snapshot:** `people[]` is one entry per person with aliases merged, and every `Commit.author` names its merged person. Aliases merge by `.mailmap` (git's `--use-mailmap` already applies it), by an exact, non-empty author name shared by two emails (the human accepted that two people of one name merge, 2026-11-25), and every email of yours into you. `isBot` (new, optional) flags a bot or agent author: a `[bot]` account (its email's local part or its name), a no-reply local part (`noreply@`, `no-reply@`, `donotreply@`: Claude Code on the web, Codex cloud, Antigravity, GitHub), a known agent's email (`src/core/crew.ts`, seeded from `docs/research/agent-providers.md`) or an agent's GitHub noreply login (`copilot`, `kiro-agent`, `openhands-agent`, `junie-agent`). A new agent identity in that doc gets a row in `AGENT_EMAILS` or `AGENT_LOGINS` and in `test/crew.test.ts`. A person's own `<id>+<login>@users.noreply.github.com` is not a bot. Bots are never merged by name; an email of yours is never a bot. A person's id is `'p_' + sha256(email)[:12]` of your primary email for you, else of the group's first email by codepoint; its `displayName` is the name on its first window commit. No raw email is stored or served (Rule 2).
- **You (captain, C9):** your emails are every `user.email` value (`git config --get-all`; the effective one is the primary) and every `commet.selfEmail` value (multi-valued git config, local or global; no UI or CLI sets it yet), each canonicalised with `git check-mailmap` and lowercased (system design §5.1.9). The same set decides `isSelf` for attribution, so only your own emails ever make a commit `human`: a name alias merges people in the crew but never makes a commit yours (Rule 1). `selfPersonIds` is your primary email's id; the crew member with it is the captain.
- **`CrewView`:** `members` (`person`, `displayName`, `seed` = uint32 of sha256(person), `captain`), sorted by `person` (codepoint), never by activity; `total` (`members.length`), `bots` (bot and agent authors left out, counted: Rule 1) and `needsRescan`. **No count of any kind per person** (Rule 6): no touches, files, planets, commits or dates in the list.
- **`CrewDetail` (Rule 6's astronaut-panel exception, human 2026-11-25):** for the one person asked, `planets` (each body they touched, a planet's `DirId` or `'star'`, from the fog's `FogBase.home` map) and `files` (each file at HEAD they touched, with its repo-relative `path` and `home`), each with `touches`: the distinct window commits of theirs that changed its content (the fog's per-file touches, renames followed to the file at HEAD; a pure rename or mode change is no touch; a merge commit's first-parent changes count for its author). `otherFiles` counts the other paths their commits changed that lead to no file at HEAD (deleted, or history the fog can't follow), never named (Rule 1). `lastActive` is the latest author date of their window commits (git's, never the clock). Bodies are sorted by `home`, files by folder then name (codepoint), never by count. No total: the answer describes one person, never ranks, compares or sums people, and never turns a number into a score.
- **Query:** exactly `person` and `at`, each once. `at` is the `CrewView.head` the view shows and must be the current head, else `ChartUnknownHead` (409). A malformed query is 400; a person the snapshot lacks, or a bot, is 404 with a fixed error naming neither. GET only, behind the same Host, origin and token gates.
- **Source:** the snapshot and the fog's base through `openFogSource`, so #64's pair check refuses a snapshot and layout from different scans here too. `crewProblem` (`src/core/crew.ts`) checks the stored people (well-formed unique ids, names, `isSelf`, `isBot` on all or none) and the author dates; a record that fails, or a person no window commit is by, is damaged state (500 with the "run `commet scan`" message).
- **`needsRescan`:** true when the snapshot predates #207 (people without `isBot`): bots can't be told from people, so the crew is empty, a member's panel has no planets, files or `lastActive`, and the view says "rescan to see your crew". No schema bump.
- **Known limit:** the window is HEAD's first-parent line (system design §5.1), so a teammate whose work only arrives inside merge commits isn't in the crew; the merge's author is, with its changes.
- **Determinism:** a pure function of the snapshot. Two scans of the same repo give byte-identical `canonicalJson`. Fixture: `test/fixtures/crew/` (an invented crew: you, five teammates, a bot and an agent author; every alias case), golden `test/golden/crew.json`.

## Local HTTP surface (`commet open`)
- **Bind and Host:** binds 127.0.0.1 only. `Host` must be `127.0.0.1:<port>` or `localhost:<port>`.
- **Token:** the opened URL is `http://127.0.0.1:<port>/#t=<token>`. The fragment is never sent to the server. The view reads it and sends `x-commet-token` on every data request.
- **Static bundle:** served at `/` from `dist/web` without a token, because it holds no repo data. No directory listing and no traversal.
- **Read routes:** `GET /api/snapshot`, `/api/layout`, `/api/fog`, `/api/unseen`, `/api/diff`, `/api/drones` (#80), `/api/drone-detail` (#148, see "Drone detail"), `/api/beacons` (#79), `/api/cochange` (#211, see "Co-change"), `/api/crew` and `/api/crew-detail` (#207, see "Crew"), GET only, behind the same Host, origin and token gates.
- **Write routes:** `POST /api/chart` with a `ChartAction` JSON body (exact keys, `at` a full 40-hex SHA, or 64-hex in a SHA-256 repo) returns a `ChartResult` (its `fog` is `fog.2` since #201). There is no route for a quiz pass. An unknown `at` gets `ChartUnknownHead` with status 409 Conflict, told apart from other refusals (400) by its `head`. `POST /api/beacon` (#79) takes a `BeaconAction` JSON body (exactly `fileId`, `at`, `text`; `application/json`, UTF-8, at most 4096 bytes) and returns a `BeaconResult`: 200 with the new `BeaconView`, 409 `ChartUnknownHead`, or 400 with a fixed reason (not a beacon, a note the rule refuses, a file not at that head, the cap). The view has no removal, so the API takes none; removal is the CLI's. Both write bodies must be UTF-8: a body that isn't is refused with 400 (`body is not UTF-8`) before it's parsed, never decoded with U+FFFD in place of its bytes (#184). Every other method or path is refused.
- **Reviewing from the view (amended 2026-11-11, #75):** two more read routes, so a file can be charted where its diff is read (R5).
  - `GET /api/unseen?home=<DirId>|star&at=<Sha>` (`UnseenQuery`, `UnseenList`) lists the fogged files of one planet, or of the star, with their paths. Layout has no file paths and leaves out surface overflow, and fog.1 has no file-to-planet map, so the view can't name them otherwise. fog.1 is unchanged.
  - `GET /api/diff?fileId=<FileId>&at=<Sha>` (`DiffQuery`, `DiffView`) is one file's unseen diff, as parsed hunks.
  - Both take exactly their two keys, each once. `at` is the `FogView.head` the view shows and must be the current head, else `ChartUnknownHead` (409) and the view refetches. Unknown ids get 404 with a fixed error naming neither the id nor a path.
  - **The client sends `at`, never `since` or a path.** The server takes the path from the snapshot and the range from its own fog: `base..at`, where `base` is the first-parent parent of the file's oldest unseen change (the empty tree at the root commit). So a stale or forged request can't narrow the diff (Rule 1), and the range ends at the same `at` the Chart action posts. `FileFog.since` minus one isn't the base: for a window gap, `since` is the commit after the gap, so `since^` would leave the gap's own change out.
  - A rename inside the range is followed: the path the file had at `base` is diffed too, so git shows the rename and its edits. When git doesn't pair them there are two sections, the old half `deleted`.
  - git runs argv-only (system design §9 check 8): `diff-tree` between the two commits (never the work tree or index), `--literal-pathspecs` (a file named `*.ts` or `:(glob)x` means only itself), `--no-ext-diff --no-textconv --no-color`, the scan's pinned config, revisions as full hex from the snapshot and paths only after `--`.
  - Past `DIFF_LIMITS` (1 Mi characters or 20,000 lines) the rest is cut and `truncated` set; the view says so beside Chart and offers the `git diff` command. At most 4 diffs run at once and each gets 10 s; past either the answer is 503.
  - Diffs are served on demand and never stored, cached or logged, on either side.
- **Live updates:** `GET /api/events` is a `text/event-stream` read with `fetch`, so the token stays in a header. Each `data:` line is a `LiveEvent`. The view refetches the named resource. A change to `beacons.json` (from this server or `commet beacon`) is sent as `{ type: 'beacons', head }` (#79), `head` the beacon view's.
  - **Rescans without hooks (amended 2026-11-16, #95):** while it runs, `commet open` watches its worktree's HEAD and the branches (read-only: that worktree's own `HEAD`, `refs/heads/**`, `refs/remotes/**`, `packed-refs` and `reftable/tables.list`, by lstat; fs.watch hints plus a poll; another worktree's HEAD moves no branch its scan shows) and, once a burst of changes settles (500 ms, at most 5 s), runs one child `commet scan` of its worktree, coalesced through `commet hook refresh`'s lock and request (one running, one pending). The child is spawned from an argv array with no shell and no terminal (it never asks and never writes `config.json`); nothing is written to git config or a hooks dir. No HTTP route starts a scan. A failed rescan is said on stderr with the scan's own message and sent as `RescanEvent` `{ type: 'rescan', ok: false, exitCode }`, also to each view that connects until a rescan works again; the first good one after it as `{ ok: true, exitCode: 0 }`. The view keeps saying the failure in its status line, after reloads too, until then. The new data itself arrives as snapshot, layout and fog events. Shutdown stops watching and kills the running child only while holding `publish.lock`, so the child is never stopped halfway through publishing its pair: it waits for that lock for as long as the child runs, and a child that ends meanwhile isn't signalled.
- **No CORS headers,** and cross-origin writes are refused.

## Render hook (R8)
- **Test mode:** only with `?test=1` (`TEST_MODE_PARAM`). There is no animation loop, and `window.__commet: RenderHook` is exposed. Without the parameter, the hook doesn't exist.
- **Calls:** `load(input)`, then `renderFrame(n)`, which draws exactly frame `n` and returns `renderer.info` draw calls and triangles. `lowResPixels()` returns the internal target before upscale, so goldens can sit near a 0 threshold.
- **Determinism:** a frame is a pure function of (`RenderInput`, frame number), per principle 3.
- **Drones (amended 2026-11-13, #80):** `RenderInput.drones` (a `DroneView`, default none) is drawn like the live view draws it: at most 16 placed sessions, the most recently ended, each circling its home. The hook checks it with the view's validator and refuses a bad one.
- **Beacons (amended 2026-11-18, #79):** `RenderInput.beacons` (a `BeaconView`, default none) must be of the layout's head and pass the view's validator, else the hook refuses it. One draw call for every body holding notes; with none, a frame is exactly what it was before beacons.
- **Palette check (amended 2026-11-10):** `RenderInput.depthFade` (default true) switches the per-pixel depth fade. With it off, off-palette pixels must be 0 (system-design §10), because the fade is the only off-palette output.
